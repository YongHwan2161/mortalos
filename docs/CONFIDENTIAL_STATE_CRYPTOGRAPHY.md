The ADR passed immutable independent review and was promoted to `main` before any
runtime implementation began. The S4 runtime remains a candidate until its exact
receipt, complete repository gates, independent immutable implementation review,

## 1. Decision

MortalOS S4 will use one versioned suite:

`mortalos-confidential-state-suite/1`

| Purpose | Required primitive |
| --- | --- |
| Chunk authenticated encryption | AES-256-GCM with a 128-bit tag |
| GCM IV | One deterministic 96-bit IV per encryption invocation under one epoch key |
| Epoch-key distribution | RSA-OAEP with a 3072-bit modulus, public exponent 65537, SHA-256, and MGF1-SHA-256 |
| Counter-reservation authentication | Ed25519 using the existing strict RFC 8032 public-key and signature profile |
| Hash and public commitments | SHA-256 with existing MortalOS domain separation |
| Canonical metadata | RFC 8785 JCS encoded as UTF-8 |
| Random keys | WebCrypto `generateKey`; no application PRNG or password-derived key |

AES-GCM is the authenticated-encryption mode defined by
[NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final). RSA-OAEP is the
key-establishment scheme defined by
[RFC 8017](https://www.rfc-editor.org/rfc/rfc8017.html). Both are exposed by the
[W3C Web Cryptography API](https://www.w3.org/TR/WebCryptoAPI/). RSA-OAEP is used
only to wrap a random 256-bit epoch key; it never encrypts resource content.

This is a standards-only composition. MortalOS will not implement AES, GCM, RSA,
OAEP, MGF1, or SHA-256. It will validate inputs, construct canonical context bytes,
allocate IVs, and call WebCrypto.

No secret key is derived in suite 1. AES and RSA keys are generated by WebCrypto;
there is no HKDF, password KDF, shared signing/encryption key, or deterministic
content key. Every public SHA-256 commitment or signed authorization message uses
the exact UTF-8 prefix below, followed by one `0x00` byte and the canonical bytes:

| Commitment | Domain prefix |
| --- | --- |
| Custodian encryption-key digest | `MortalOS S4 encryption public key v1` |
| Counter-authority ID | `MortalOS S4 counter authority v1` |
| Counter-reservation signature message | `MortalOS S4 counter reservation v1` |
| Counter-reservation receipt digest | `MortalOS S4 counter receipt v1` |
| Epoch ID | `MortalOS S4 epoch id v1` |
| Chunk AAD digest | `MortalOS S4 chunk aad v1` |
| Ciphertext-chunk digest | `MortalOS S4 ciphertext chunk v1` |
| Wrap-label digest | `MortalOS S4 wrap label v1` |
| Wrapped-key digest | `MortalOS S4 wrapped epoch key v1` |
| Confidential package root | `MortalOS S4 confidential package v1` |
| Confidential transition receipt | `MortalOS S4 confidential receipt v1` |
| Rotation-authorization signature message | `MortalOS S4 rotation authorization v1` |

S4 changes no `mortalos/0` or `mortalos/1` validation rule. It adds exact
`mortalos-confidential-*/1` sidecars carried as the bounded raw S3 resource. The
existing v1 public resource root therefore commits ciphertext-package bytes, not
plaintext bytes. Unknown confidential sidecars remain invalid until their
versioned dispatcher is explicitly implemented.

## 2. Claim and non-claims

### Promotable claim

Assuming the exact epoch-bound counter authority follows its linearizable
non-overlap contract and its signing key is not compromised, an operator that sees
only an S4 relay or remote-store capture cannot recover resource plaintext or an
unwrapped epoch key. A custodian removed at epoch `N` does not receive the epoch
`N+1` key and cannot decrypt state first created under epoch `N+1`, while an
authorized surviving custodian with its bound private decryption key can.

### Explicit non-claims

- S4 does not provide retroactive secrecy. A former custodian may retain plaintext,
  an old epoch key, or old ciphertext that it could read while authorized.
- S4 does not prove secure erasure from JavaScript memory, browser storage, backups,
  operating systems, remote providers, or a malicious custodian.
- A non-extractable WebCrypto key blocks supported API export; it does not resist a
  compromised process, browser, OS, hardware, or user account.
- S4 trusts the epoch-bound counter authority not to sign overlapping reservation
  histories. Compromise of that authority can violate nonce uniqueness; suite 1
  detects a fork only when conflicting receipts are jointly observed and then
  retires the key. It cannot undo prior exposure or detect a hidden fork, and does
  not provide Byzantine allocation.
- Any one authorized custodian receives a wrap it can decrypt. Quorum controls
  lineage mutation, not read access by an already authorized custodian.
- Encryption does not prove protocol validity, availability, liveness, physical
  independence, Byzantine resistance, or death.
- S4 does not hide traffic timing, participant count, ciphertext length, chunk
  count, epoch number, membership changes, resource identifiers, or access patterns.

## 3. Protected and public values

### Secret at authorized endpoints

- plaintext resource bytes;
- the random 256-bit epoch content-encryption key;
- each custodian's RSA-OAEP private key;
- the counter authority's Ed25519 private key; and
- transient plaintext produced only after complete authenticated decryption.

The epoch key exists first as a short-lived extractable WebCrypto staging key only
because `wrapKey` must serialize it internally. Application code never calls
`exportKey` on that handle. Every durable authorized handle is produced by
`unwrapKey` as a non-extractable, decrypt-only AES-GCM key. The recovered handle
cannot invoke encryption; encryption is possible only with the fresh staging key
after a counter interval has been durably reserved. The staging handle is discarded
before activation. The RSA private key is generated non-extractable with
`unwrapKey` usage only. Application code must not export, serialize, log, or
transmit either secret.

### Public and capturable

- suite and format identifiers;
- organism and resource identifiers;
- epoch number and membership-head digest;
- RSA public encryption keys and their digests;
- the counter-authority Ed25519 public key and authority ID;
- recipient identifiers;
- per-record invocation counters and IVs;
- canonical associated-data metadata;
- ciphertext lengths, ciphertext bytes, authentication tags, and ciphertext
  digests;
- recipient-specific RSA-OAEP wrapped epoch keys; and
- signed state-package manifests and transition receipts.

Public state roots commit the confidential package, not a public digest of raw
plaintext. A plaintext digest required for authorized reconstruction is itself
inside the encrypted payload. This avoids turning a public plaintext hash into a
dictionary oracle.

## 4. Custodian encryption keys

Each participant has a signing key and a distinct encryption key. The encryption
key pair is:

- algorithm `RSA-OAEP`;
- modulus length `3072`;
- public exponent `65537`;
- hash `SHA-256`;
- public key exportable as canonical SPKI bytes; and
- private key non-extractable with `unwrapKey` usage only.

The public-key SPKI bytes and their domain-separated digest are bound into the
custodian descriptor. A new custodian acceptance signs the exact descriptor,
including its encryption-key digest. A signing key cannot silently substitute a
different encryption key, and an encryption key never grants signing authority.

Unknown algorithms, modulus lengths, exponents, hashes, key usages, encodings, or
duplicate encryption-key digests fail closed before any wrap or unwrap.

## 5. Epoch key and identity

An accepted confidential epoch contains:

- a strictly increasing unsigned 64-bit `epoch`, encoded in every JCS document as
  its canonical decimal string;
- the exact accepted membership-head digest;
- a fresh WebCrypto-generated AES-256-GCM key;
- an epoch-wide, linearizable 64-bit invocation high-water mark, encoded as its
  canonical decimal string;
- one wrap for every and only current custodian;
- one or more completely encrypted resource packages; and
- an atomic active-epoch record.

The public `epoch_id` is a MortalOS domain-separated SHA-256 commitment to the
canonical suite, organism ID, canonical decimal epoch string,
membership-head digest, transition ID, counter-authority ID, exact strict
Ed25519 counter-authority public key, and sorted current custodian encryption-key
digests. It is not derived from a secret key. Changing the counter authority or
its key therefore requires a fresh epoch key and a new `epoch_id`.

The exact epoch-ID basis is:

```json
{
  "counter_authority_id": "sha256:...",
  "counter_authority_public_key": "ed25519:...",
  "custodian_encryption_keys": ["sha256:..."],
  "epoch": "0",
  "format": "mortalos-confidential-epoch-id/1",
  "membership_head": "sha256:...",
  "organism_id": "mortalos:...",
  "suite": "mortalos-confidential-state-suite/1",
  "transition_id": "transition-1"
}
```

Custodian encryption-key digests are strictly sorted, unique, and cover every and
only current custodian. The epoch ID is the tagged SHA-256 result of the
`MortalOS S4 epoch id v1` domain, one `0x00` byte, and these exact JCS bytes.

An epoch string is `"0"` or a non-zero ASCII decimal integer with no leading zero,
in the closed range `0` through `18446744073709551615`. Implementations compare it
as an unsigned 64-bit integer (for example with `BigInt`) and never coerce it to a
JSON number. This rule applies to the epoch in every ID basis, AAD, wrap label,
manifest, reservation, package, receipt, and active record.

An epoch key is never reused for another `epoch_id`, another organism, or a changed
membership. Accepted membership change always creates a fresh epoch key and
increments the epoch.

## 6. IV allocation and collision rule

AES-GCM requires IV uniqueness under a given key. MortalOS uses only the
deterministic 96-bit construction:

```text
iv = 0x4d4f5334 || uint64_be(invocation_counter)
```

`0x4d4f5334` is the fixed four-byte S4 record-suite field. The counter is unique
under one epoch key and is encoded as an unsigned 64-bit integer. Suite 1 permits
at most `2^32` encryption invocations under one epoch key, with counters `0`
through `2^32 - 1`; the wider encoding is reserved for format stability, not a
larger security claim. Reaching the cap requires a fresh epoch key before another
encryption.

Counter allocation is epoch-wide, not endpoint-local. Every writer for one
`epoch_id` must use the same linearizable `reserveRange(expectedHighWater, count)`
authority. A reservation atomically compares the expected high-water mark, commits
one non-overlapping half-open counter interval, and returns a canonical,
authenticated reservation receipt binding the authority ID, `epoch_id`, prior and
next high-water marks, interval, request ID, and count. The confidential package
commits that receipt and each chunk commits one counter within its interval.

The counter authority is part of the S4 confidentiality TCB. It is not the relay
or a per-browser storage object, and a caller cannot substitute a local allocator
after failover. The reference adapter must provide linearizable compare-and-swap
across processes and endpoints. A future physical deployment must name the actual
authority and durability domain in its topology receipt; S4 alone does not claim
that domain is independently durable.

The authority never dispatches through caller-visible store methods after
construction. Each conforming reference store registers one immutable
module-private capability record while its constructor still owns the instance;
that record contains closures over private inspect and transaction operations.
The branded authority and every facade resolve only that private record. Replacing
an instance or prototype `inspect`/`transact` method before or after authority or
facade creation therefore cannot manufacture loss, retirement, or equivocation.

The browser reference adapter persists the non-extractable Ed25519 private key and
epoch records by structured clone in one versioned IndexedDB database. An
origin-scoped exclusive Web Lock serializes conforming callers across tabs and
renderer processes, while the IndexedDB record revision supplies a second
compare-and-swap check before commit. Reopening the same persistent browser profile
after full Chromium process termination must recover the same authority ID,
non-extractable sign-only key, receipt-chain digest, and next counter. This proves
reference failover within that storage/credential domain; it does not prove the S7
independence of that domain.

The authority owns a distinct WebCrypto-generated Ed25519 key pair. Its private key
is non-extractable with `sign` usage only. Its public key is the exact strict
32-byte RFC 8032 encoding tagged `ed25519:`. The `authority_id` is the tagged
SHA-256 result of the `MortalOS S4 counter authority v1` domain, one `0x00` byte,
and those 32 raw public-key bytes. Both the ID and public key are bound into the
`epoch_id`; neither a local key nor another authority can validate for that epoch.

The exact reservation signature basis is this JCS object:

```json
{
  "authority_id": "sha256:...",
  "authority_public_key": "ed25519:...",
  "count": "16",
  "epoch": "0",
  "epoch_id": "sha256:...",
  "format": "mortalos-counter-reservation-basis/1",
  "interval_end_exclusive": "16",
  "interval_start": "0",
  "next_counter": "16",
  "prior_next_counter": "0",
  "prior_receipt_digest": null,
  "request_id": "reservation:...",
  "suite": "mortalos-confidential-state-suite/1"
}
```

The signature message is exactly SHA-256 over the UTF-8 bytes
`MortalOS S4 counter reservation v1`, one `0x00` byte, and the JCS bytes of
that basis. The authority signs those 32 bytes with Ed25519. The complete canonical
receipt has exactly three keys:

```json
{
  "basis": {
    "authority_id": "sha256:...",
    "authority_public_key": "ed25519:...",
    "count": "16",
    "epoch": "0",
    "epoch_id": "sha256:...",
    "format": "mortalos-counter-reservation-basis/1",
    "interval_end_exclusive": "16",
    "interval_start": "0",
    "next_counter": "16",
    "prior_next_counter": "0",
    "prior_receipt_digest": null,
    "request_id": "reservation:...",
    "suite": "mortalos-confidential-state-suite/1"
  },
  "format": "mortalos-counter-reservation-receipt/1",
  "signature": "ed25519:..."
}
```

The signature is the existing strict tagged 64-byte Ed25519 encoding. The receipt
digest is SHA-256 over
the `MortalOS S4 counter receipt v1` domain, one `0x00` byte, and the complete
receipt JCS bytes. Each confidential package manifest commits the exact receipt
digest, `interval_start`, `interval_end_exclusive`, authority ID, and
`transition_id`. On creation and import, the verifier recomputes `epoch_id` from
the receipt's authority ID/public key, sorted wrap encryption-key digests, epoch,
membership head, organism ID, and `transition_id`. A caller-selected or
failover-local authority therefore fails before reservation or WebCrypto. Its
chunk at index `i` must use counter `interval_start + i`, and `count` must equal
the package chunk count.

The first reservation in an epoch has `prior_receipt_digest: null`. Every later
reservation carries the exact digest of the previously committed receipt. The
atomic active record stores both `next_counter` and
`last_counter_receipt_digest`. Before activation, the candidate basis must match
both active values; after activation, both advance together. A stale or unlinked
candidate is rejected without publishing its package.

The verifier checks exact keys, formats, canonical bytes, strict public key and
signature encodings, recomputed authority ID, epoch binding, receipt signature and
digest, request-ID grammar (`reservation:` plus exactly 32 base64url bytes), and
all arithmetic before accepting a reservation. It parses decimal strings with
integer arithmetic and requires:

- `count` from `1` through `64`;
- `prior_next_counter == interval_start`;
- `prior_receipt_digest` is `null` only when `prior_next_counter == "0"`, otherwise
  it is the active exact tagged receipt digest;
- `interval_end_exclusive == interval_start + count`;
- `next_counter == interval_end_exclusive`; and
- `0 <= interval_start < interval_end_exclusive <= 4294967296`.

A conforming authority's linearizable compare-and-swap emits at most one signed
successor for one `(epoch_id, prior_next_counter, prior_receipt_digest)` tuple.
Concurrent reference tests must prove exactly one success and all stale requests
must fail before encryption. If two correctly signed successors of the same tuple
are later jointly observed, the observer verifies that both bind the supplied
authority, atomically retires that bound authority, confirms its retired state, and
only then returns runtime-branded `counter_authority_equivocation` evidence. The
observer blocks both receipts from new activation and starts the authority-only
rotation below. A cloned or caller-created evidence object has no authority. Either
receipt in isolation remains
cryptographically valid; suite 1 makes no hidden-fork detection claim.

Before encryption, a writer waits until its reservation is durably committed and
independently verifies the receipt. Only then may it call WebCrypto. Reservation
is monotonic and never rolled back. A crash may leave a gap; it must never permit
reuse. A stale writer, conflicting concurrent request, duplicated interval,
counter decrease, counter overflow, unknown or lost authority state, invalid
receipt, local-only allocator, mixed deterministic/random IV construction, or
suite-cap exhaustion fails before WebCrypto is called. If authoritative state
cannot be recovered exactly, the key is retired and a fresh epoch key is required;
scanning visible ciphertext must not reconstruct authority because a previously
reserved but unpublished IV may be absent.

The following representation matrix is exhaustive. Every listed field is a JCS
string; the same value encoded as a JSON number, exponent, signed value,
whitespace-padded value, empty string, or leading-zero decimal is invalid.

| Surface | Decimal-string fields | Inclusive range |
| --- | --- | --- |
| Epoch-ID basis, reservation basis, AAD, wrap label, manifest, package, receipt, active record | `epoch` | `0` through `18446744073709551615` |
| Reservation basis and package manifest | `count` | `1` through `64` |
| Reservation basis, package manifest, active record | `prior_next_counter`, `interval_start`, `interval_end_exclusive`, `next_counter` as applicable | starts `0` through `4294967295`; exclusive end / next `1` through `4294967296` |
| Chunk AAD and package chunk entry | `invocation_counter` | `0` through `4294967295` |

Boundary vectors must accept epoch strings `9007199254740991`,
`9007199254740992`, and `18446744073709551615`; reject epoch
`18446744073709551616`; accept final counter interval
`4294967295..4294967296`; and reject any counter, invocation, or exclusive end
beyond `4294967296`. They also reject JSON-number forms at `2^32`, `2^53`, and
`2^64`, even when a host language would round or preserve the apparent value.

Counter values may repeat after an epoch rotation because the AES key is fresh.
They may not repeat under the same key. Imports verify that all IVs are exactly 12
bytes, use the fixed field, are unique within the package, fall within the exact
committed reservation, and do not exceed the accepted epoch-wide high-water
evidence.

The implementation gate generates at least 1,000,000 records from concurrent
writers sharing one epoch authority and must observe exactly 1,000,000 distinct IV
byte strings. It also injects cross-endpoint failover, stale, duplicate, honest
CAS conflict, jointly observed valid overlap, overflow, rollback, lost-authority,
local-allocator, and concurrent reservations.

## 7. Canonical associated data

Every encrypted chunk uses a 128-bit GCM tag and canonical UTF-8 AAD with exact keys:

```json
{
  "chunk_count": 0,
  "chunk_index": 0,
  "epoch": "0",
  "epoch_id": "sha256:...",
  "format": "mortalos-confidential-chunk-aad/1",
  "invocation_counter": "0",
  "membership_head": "sha256:...",
  "organism_id": "mortalos:...",
  "plaintext_bytes": 0,
  "prior_confidential_root": "sha256:...",
  "resource_id": "mortalos-resource:...",
  "suite": "mortalos-confidential-state-suite/1"
}
```

The counter is a canonical decimal string to avoid JSON number precision loss.
Exact limits, identifier grammars, property set, property order after JCS, and
byte ceilings are normative. Plaintext is at most 65,536 bytes per invocation,
AAD at most 4,096 bytes, and ciphertext exactly plaintext length plus the 16-byte
GCM tag. AAD is supplied to WebCrypto as `additionalData`; it is also committed by
digest in the confidential manifest.

The ciphertext digest is computed after encryption and therefore is not part of
its own AAD. The signed manifest binds the AAD digest, IV, ciphertext digest,
ciphertext length, tag length, and ordered chunk position.

No decrypted byte becomes visible to the caller until every selected chunk passes
GCM authentication, all declared lengths and positions match, the ordered
plaintext is reconstructed in an isolated buffer, and the encrypted internal
resource commitment matches. Any failure discards the candidate plaintext and
returns one stable non-oracular error.

## 8. Epoch-key wraps

For each current custodian, WebCrypto `wrapKey("raw", ...)` wraps the short-lived
AES-GCM staging key under that custodian's exact bound public key. The OAEP label is
the canonical UTF-8 encoding of:

```json
{
  "custodian_encryption_key": "sha256:...",
  "custodian_id": "mortalos-key:...",
  "epoch": "0",
  "epoch_id": "sha256:...",
  "format": "mortalos-epoch-wrap-label/1",
  "membership_head": "sha256:...",
  "organism_id": "mortalos:...",
  "suite": "mortalos-confidential-state-suite/1"
}
```

The wrap record contains the exact label digest, recipient/key identifiers, suite,
epoch, and exactly 384 wrapped bytes for the 3072-bit modulus. Wrap records are
sorted by custodian ID, have no duplicate recipient or public-key digest, cover
every current custodian exactly once, and contain no removed custodian.

`unwrapKey("raw", ...)` uses the same label bytes and the locally bound
non-extractable private key, and creates a non-extractable AES-GCM key. OAEP
failure, wrong recipient, wrong label, substituted public key, stale epoch,
duplicate wrap, missing current wrap, removed-member wrap, or unexpected key length
returns one stable wrap error and releases no candidate epoch key.

## 9. Encrypt, recover, and activate

Encryption is layered over S3:

1. Validate the accepted lineage, membership descriptor, resource limits, and
   confidential transition input.
2. Reserve all required invocation counters through the shared epoch-wide
   linearizable authority and verify its committed receipt.
3. Encrypt fixed bounded plaintext chunks locally with exact AAD.
4. Construct and verify the ciphertext-only package and every current-member wrap.
5. Store and replicate only ciphertext packages through S3 adapters.
6. Recover ciphertext using S3 inventory/fetch/digest rules.
7. An authorized endpoint unwraps the epoch key and authenticates every chunk.
8. Reconstruct exact plaintext privately and verify its encrypted internal
   commitment.
9. Atomically activate the completely verified epoch/package.

Relay presence, store inventory, ciphertext digest success, OAEP unwrap success, or
GCM decrypt success alone never accepts a lineage transition. The existing protocol
validator accepts only the exact quorum-signed canonical package and receipt.

Missing ciphertext remains `state_unavailable`. Missing local decryption authority
is distinct `key_unavailable`. Authentication or semantic mismatch is
`confidential_state_rejected`. Adapter interruption is
`confidential_state_interrupted`. Error details must not reveal whether a guessed
plaintext, key, tag, label, or individual chunk was close to valid.

## 10. Membership or authority rotation and crash semantics

An accepted rotation from epoch `N` to `N+1` requires:

1. an exact `mortalos-confidential-rotation-authorization/1` document. Unique,
   strictly sorted current-custodian signatures must meet the threshold in a
   module-private, validator-branded current Genesis/Pulse head. A caller-written
   `"accepted"` value, cloned head, or structurally similar object is not authority;
2. signatures over the domain-separated exact rotation basis, binding the current
   and approved membership heads, organism, old/new epochs, next counter-authority
   ID, sorted unique resulting encryption-key digests, suite, and exactly one
   reason: `membership_change`, `counter_authority_lost`, or
   `counter_authority_equivocation`;
3. for membership change, a validator-branded direct-child membership Pulse,
   changed encryption-key set, and exact new-custodian acceptance; otherwise the
   exact unchanged head and encryption-key set;
4. for authority loss or equivocation, a fresh strict Ed25519 counter-authority key
   and ID. Loss requires an exact-constructor authority or a frozen persistent
   facade bound to that authority's module-private WeakMap record; public
   `descriptor`, `reserveRange`, `inspect`, and `retire` methods are never trusted
   for this decision or successor construction. The successor input is captured
   once as an inert own-data record before authorization checks, and its exact
   branded authority capability supplies both the approved descriptor and every
   reservation through module-private dispatch. A stateful accessor therefore
   cannot present approved authority `X` and later construct authority `Y`. Its
   authoritative epoch state must be inaccessible. Equivocation
   requires runtime-branded jointly observed evidence and direct retirement plus
   inspection through that same private record. Subclasses, proxies, prototype
   lookalikes, caller objects, and cloned evidence are not authority. For
   membership-only change, the prior healthy authority may remain;
5. a fresh AES epoch key and reset counter chain;
6. wraps for every and only the resulting membership;
7. complete re-encryption of the active plaintext under epoch `N+1`; and
8. atomic activation of the resulting membership, confidential package, wraps,
   epoch-wide counter-authority binding and state, and active-epoch record.

Authority loss or equivocation immediately disables new encryption under epoch
`N`. It does not require a membership change, and the compromised authority cannot
authorize its own replacement: the existing MortalOS quorum authorizes the
rotation input and exact successor package. If an authorized custodian can still
decrypt the active epoch, it re-encrypts for the same membership under the fresh
epoch and authority. If no authorized endpoint can decrypt, the result is
`key_unavailable`; it is never empty state, invalid lineage, or death.

Every write boundary must recover to one of two complete states:

- old configuration plus complete readable epoch `N`; or
- quorum-authorized resulting configuration plus complete readable epoch `N+1`.

A mixed membership/key/package state is never active. Until the final atomic commit,
epoch `N` remains the only active state and its ciphertext, wraps, and local key
material are retained. After commit, best-effort deletion may remove local old keys
and staged bytes, but no erasure claim follows.

A custodian removed at `N` receives no `N+1` wrap. Tests give it the complete public
`N+1` capture, every old key and wrap, and its removed private key; decryption must
still fail. Authorized survivors must decrypt exact `N+1` bytes.

If one current encryption key is lost, any surviving authorized custodian that can
decrypt the old epoch may participate in a quorum-approved membership repair and
fresh epoch rotation. If no authorized endpoint can recover an epoch key, state is
`key_unavailable`; it is not empty state, invalid lineage, or death.

## 11. Metadata leakage and capture gate

The public capture leaks the values listed in section 3, including equality and
size patterns within the limits implied by ciphertext structure. S4 does not add
padding in version 1. Applications with sensitive length distributions require a
future versioned padding ADR.

The capture test records every byte offered to the relay and remote-store adapters,
then rejects if it contains:

- the reference plaintext or any designated plaintext marker;
- the raw 32-byte epoch key;
- a private signing or RSA key encoding;
- an unwrapped WebCrypto key export;
- a public plaintext digest designated as confidential; or
- an unexpected unencrypted payload field.

Passing a marker scan is not itself proof of encryption. The test also independently
parses every record as a bounded ciphertext/wrap format and proves exact authorized
decryption from the captured bytes plus only the recipient private key.

## 12. Versioning and migration

All formats and the suite ID are exact. Unknown versions or algorithms fail closed.
A package cannot mix suites, IV constructions, tag lengths, wrap algorithms, or
epoch numbers.

Algorithm migration is a membership-authorized confidential-state transition:

1. approve a new ADR and new suite identifier;
2. retain the old complete readable epoch;
3. decrypt under the old supported suite at an authorized endpoint;
4. create a fresh key and complete package under the new suite;
5. cross-runtime verify both sides; and
6. atomically activate the new suite or retain the old epoch.

Silent parameter upgrades are forbidden. RSA key-size change, hash change, tag
change, padding, multi-resource nonce allocation, hardware-backed keys, or a future
post-quantum/hybrid wrap each requires a new suite.

## 13. Required implementation evidence

S4 implementation remains HOLD until all of the following pass on one frozen source:

- NIST AES-GCM known-answer and negative vectors;
- published RSA-OAEP SHA-256 decrypt/label vectors and malformed-ciphertext
  negatives;
- byte-identical Node WebCrypto and actual Chromium vectors;
- exact JCS AAD and wrap-label fixtures;
- at least 1,000,000 IV allocations from concurrent endpoints sharing one
  epoch-wide linearizable authority with zero duplicates, plus failover,
  local-only allocation, lost-authority, rollback, stale, and overflow rejection;
- actual Chromium two-endpoint contention with exactly one CAS winner, followed by
  full browser-process termination and recovery of the same non-extractable
  authority key, receipt chain, and next counter from a persistent profile;
- store own/prototype `inspect` and `transact` replacement before and after
  authority/facade construction has no effect, and actual Chromium IndexedDB/Web
  Locks facades complete both lost-authority and observed-equivocation rotations;
- conforming CAS conflict tests with exactly one signed successor per prior tuple;
  jointly observed valid overlapping receipts produce explicit authority
  equivocation and authority-only rotation, while hidden-fork detection remains an
  explicit nonclaim;
- relay and store capture with zero plaintext, raw epoch key, private key, or public
  confidential digest;
- recovered epoch keys are non-extractable and decrypt-only, and a direct WebCrypto
  encryption attempt with a recovered handle is rejected;
- any-two S3 ciphertext recovery followed by exact authorized decryption;
- removed-at-`N` future-epoch denial and authorized-survivor success;
- literal, empty, cloned, forged, wrong-signer, reused-authority, and
  membership-change-under-authority-only rotation authorization is rejected;
- replay, substitution, truncation, reorder, wrong-resource, wrong-membership,
  wrong-epoch, wrong-label, duplicate-wrap, and authentication-tag rejection with
  no partial plaintext;
- fault injection at every counter, chunk, wrap, package, rotation, and activation
  write boundary, yielding only complete old or complete new epoch;
- unchanged v0/v1 lineage, mortality, S1, S2, and S3 behavior;
- exact receipt `evidence/stages/s4-confidentiality.json`;
- zero high-or-higher and zero total dependency advisories; and
- immutable independent review, expected-head merge, exact-main Verify, Deploy,
  and public readback.

## 14. Rejected alternatives

- **Plaintext at trusted relay:** contradicts the S4 operator-capture threat model.
- **AES-GCM with random 96-bit IVs:** probabilistic collision management is
  unnecessary when a durable deterministic invocation field is available.
- **One nonce derived only from chunk index:** re-encrypting changed content under
  the same epoch could reuse a nonce.
- **RSA-PKCS1-v1_5:** retained by RFC 8017 for compatibility, not selected for new
  key establishment.
- **Reuse Ed25519 signing keys for encryption:** conflates authority and
  confidentiality and is not a valid WebCrypto key conversion.
- **Home-grown ECDH/HPKE:** a custom KEM/KDF/AEAD composition is outside this ADR.
- **Password-derived or user-entered content keys:** creates weak-key and recovery
  ambiguity outside the participant custody model.
- **Convergent/deterministic plaintext encryption:** leaks equality and enables
  confirmation attacks.
- **Decryption as validity:** gives secret holders a second authority path and is
  forbidden.
