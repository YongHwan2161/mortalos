# S4 confidential-state cryptography

Status: **PROPOSED ADR — IMPLEMENTATION HOLD**

Decision owner: `codex-protocol-kernel`  
Independent reviewer: `reviewer-merge-gate`  
Decision base: `1f8c055f1cf6fb4ee304f0b61cbe6507c65dba7d`

No S4 runtime code may merge until this ADR passes an immutable independent review
and is promoted to `main`. The eventual implementation must use only the suite and
failure rules below; a different algorithm, encoding, nonce rule, or key lifecycle
requires a replacement ADR and fresh review.

## 1. Decision

MortalOS S4 will use one versioned suite:

`mortalos-confidential-state-suite/1`

| Purpose | Required primitive |
| --- | --- |
| Chunk authenticated encryption | AES-256-GCM with a 128-bit tag |
| GCM IV | One deterministic 96-bit IV per encryption invocation under one epoch key |
| Epoch-key distribution | RSA-OAEP with a 3072-bit modulus, public exponent 65537, SHA-256, and MGF1-SHA-256 |
| Hash and public commitments | SHA-256 with existing MortalOS domain separation |
| Canonical metadata | RFC 8785 JCS encoded as UTF-8 |
| Random keys | WebCrypto `generateKey`; no application PRNG or password-derived key |

AES-GCM is the authenticated-encryption mode defined by
[NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final). RSA-OAEP is the
key-establishment scheme defined by
[RFC 8017](https://www.rfc-editor.org/rfc/rfc8017.html). Both are exposed by the
[W3C Web Cryptography API](https://www.w3.org/TR/WebCryptoAPI/). RSA-OAEP is used
only to wrap a random 256-bit epoch key; it never encrypts resource content.

This is a standards-only composition. MortalOS will not implement AES, GCM, RSA,
OAEP, MGF1, or SHA-256. It will validate inputs, construct canonical context bytes,
allocate IVs, and call WebCrypto.

No secret key is derived in suite 1. AES and RSA keys are generated by WebCrypto;
there is no HKDF, password KDF, shared signing/encryption key, or deterministic
content key. Every public SHA-256 commitment uses the exact UTF-8 prefix below,
followed by one `0x00` byte and the canonical bytes:

| Commitment | Domain prefix |
| --- | --- |
| Custodian encryption-key digest | `MortalOS S4 encryption public key v1` |
| Epoch ID | `MortalOS S4 epoch id v1` |
| Chunk AAD digest | `MortalOS S4 chunk aad v1` |
| Ciphertext-chunk digest | `MortalOS S4 ciphertext chunk v1` |
| Wrap-label digest | `MortalOS S4 wrap label v1` |
| Wrapped-key digest | `MortalOS S4 wrapped epoch key v1` |
| Confidential package root | `MortalOS S4 confidential package v1` |
| Confidential transition receipt | `MortalOS S4 confidential receipt v1` |

S4 changes no `mortalos/0` or `mortalos/1` validation rule. It adds exact
`mortalos-confidential-*/1` sidecars carried as the bounded raw S3 resource. The
existing v1 public resource root therefore commits ciphertext-package bytes, not
plaintext bytes. Unknown confidential sidecars remain invalid until their
versioned dispatcher is explicitly implemented.

## 2. Claim and non-claims

### Promotable claim

An operator that sees only an S4 relay or remote-store capture cannot recover
resource plaintext or an unwrapped epoch key. A custodian removed at epoch `N`
does not receive the epoch `N+1` key and cannot decrypt state first created under
epoch `N+1`, while an authorized surviving custodian with its bound private
decryption key can.

### Explicit non-claims

- S4 does not provide retroactive secrecy. A former custodian may retain plaintext,
  an old epoch key, or old ciphertext that it could read while authorized.
- S4 does not prove secure erasure from JavaScript memory, browser storage, backups,
  operating systems, remote providers, or a malicious custodian.
- A non-extractable WebCrypto key blocks supported API export; it does not resist a
  compromised process, browser, OS, hardware, or user account.
- Any one authorized custodian receives a wrap it can decrypt. Quorum controls
  lineage mutation, not read access by an already authorized custodian.
- Encryption does not prove protocol validity, availability, liveness, physical
  independence, Byzantine resistance, or death.
- S4 does not hide traffic timing, participant count, ciphertext length, chunk
  count, epoch number, membership changes, resource identifiers, or access patterns.

## 3. Protected and public values

### Secret at authorized endpoints

- plaintext resource bytes;
- the random 256-bit epoch content-encryption key;
- each custodian's RSA-OAEP private key; and
- transient plaintext produced only after complete authenticated decryption.

The epoch key exists first as a short-lived extractable WebCrypto staging key only
because `wrapKey` must serialize it internally. Application code never calls
`exportKey` on that handle. Every durable authorized handle is produced by
`unwrapKey` as a non-extractable AES-GCM key, and the staging handle is discarded
before activation. The RSA private key is generated non-extractable with
`unwrapKey` usage only. Application code must not export, serialize, log, or
transmit either secret.

### Public and capturable

- suite and format identifiers;
- organism and resource identifiers;
- epoch number and membership-head digest;
- RSA public encryption keys and their digests;
- recipient identifiers;
- per-record invocation counters and IVs;
- canonical associated-data metadata;
- ciphertext lengths, ciphertext bytes, authentication tags, and ciphertext
  digests;
- recipient-specific RSA-OAEP wrapped epoch keys; and
- signed state-package manifests and transition receipts.

Public state roots commit the confidential package, not a public digest of raw
plaintext. A plaintext digest required for authorized reconstruction is itself
inside the encrypted payload. This avoids turning a public plaintext hash into a
dictionary oracle.

## 4. Custodian encryption keys

Each participant has a signing key and a distinct encryption key. The encryption
key pair is:

- algorithm `RSA-OAEP`;
- modulus length `3072`;
- public exponent `65537`;
- hash `SHA-256`;
- public key exportable as canonical SPKI bytes; and
- private key non-extractable with `unwrapKey` usage only.

The public-key SPKI bytes and their domain-separated digest are bound into the
custodian descriptor. A new custodian acceptance signs the exact descriptor,
including its encryption-key digest. A signing key cannot silently substitute a
different encryption key, and an encryption key never grants signing authority.

Unknown algorithms, modulus lengths, exponents, hashes, key usages, encodings, or
duplicate encryption-key digests fail closed before any wrap or unwrap.

## 5. Epoch key and identity

An accepted confidential epoch contains:

- a strictly increasing unsigned 64-bit `epoch`;
- the exact accepted membership-head digest;
- a fresh WebCrypto-generated AES-256-GCM key;
- a 64-bit durable invocation high-water mark;
- one wrap for every and only current custodian;
- one or more completely encrypted resource packages; and
- an atomic active-epoch record.

The public `epoch_id` is a MortalOS domain-separated SHA-256 commitment to the
canonical suite, organism ID, epoch number, membership-head digest, transition ID,
and sorted current custodian encryption-key digests. It is not derived from the
secret key.

An epoch key is never reused for another `epoch_id`, another organism, or a changed
membership. Accepted membership change always creates a fresh epoch key and
increments the epoch.

## 6. IV allocation and collision rule

AES-GCM requires IV uniqueness under a given key. MortalOS uses only the
deterministic 96-bit construction:

```text
iv = 0x4d4f5334 || uint64_be(invocation_counter)
```

`0x4d4f5334` is the fixed four-byte S4 record-suite field. The counter is unique
under one epoch key and is encoded as an unsigned 64-bit integer. Suite 1 permits
at most `2^32` encryption invocations under one epoch key, with counters `0`
through `2^32 - 1`; the wider encoding is reserved for format stability, not a
larger security claim. Reaching the cap requires a fresh epoch key before another
encryption.

Before encryption, the durable adapter atomically reserves the next counter and
persists the new high-water mark. Reservation is monotonic and never rolled back.
A crash may leave a gap; it must never permit reuse. A stale writer, duplicated
reservation, counter decrease, counter overflow, unknown high-water state, or
mixed deterministic/random IV construction, or suite-cap exhaustion fails before
WebCrypto is called.

Counter values may repeat after an epoch rotation because the AES key is fresh.
They may not repeat under the same key. Imports verify that all IVs are exactly 12
bytes, use the fixed field, are unique within the package, and do not exceed the
accepted reservation evidence.

The implementation gate generates at least 1,000,000 sequential records under one
key-allocation model and must observe exactly 1,000,000 distinct IV byte strings.
It also injects stale, duplicate, overflow, rollback, and concurrent reservations.

## 7. Canonical associated data

Every encrypted chunk uses a 128-bit GCM tag and canonical UTF-8 AAD with exact keys:

```json
{
  "chunk_count": 0,
  "chunk_index": 0,
  "epoch": 0,
  "epoch_id": "sha256:...",
  "format": "mortalos-confidential-chunk-aad/1",
  "invocation_counter": "0",
  "membership_head": "sha256:...",
  "organism_id": "mortalos:...",
  "plaintext_bytes": 0,
  "prior_confidential_root": "sha256:...",
  "resource_id": "mortalos-resource:...",
  "suite": "mortalos-confidential-state-suite/1"
}
```

The counter is a canonical decimal string to avoid JSON number precision loss.
Exact limits, identifier grammars, property set, property order after JCS, and
byte ceilings are normative. Plaintext is at most 65,536 bytes per invocation,
AAD at most 4,096 bytes, and ciphertext exactly plaintext length plus the 16-byte
GCM tag. AAD is supplied to WebCrypto as `additionalData`; it is also committed by
digest in the confidential manifest.

The ciphertext digest is computed after encryption and therefore is not part of
its own AAD. The signed manifest binds the AAD digest, IV, ciphertext digest,
ciphertext length, tag length, and ordered chunk position.

No decrypted byte becomes visible to the caller until every selected chunk passes
GCM authentication, all declared lengths and positions match, the ordered
plaintext is reconstructed in an isolated buffer, and the encrypted internal
resource commitment matches. Any failure discards the candidate plaintext and
returns one stable non-oracular error.

## 8. Epoch-key wraps

For each current custodian, WebCrypto `wrapKey("raw", ...)` wraps the short-lived
AES-GCM staging key under that custodian's exact bound public key. The OAEP label is
the canonical UTF-8 encoding of:

```json
{
  "custodian_encryption_key": "sha256:...",
  "custodian_id": "mortalos-key:...",
  "epoch": 0,
  "epoch_id": "sha256:...",
  "format": "mortalos-epoch-wrap-label/1",
  "membership_head": "sha256:...",
  "organism_id": "mortalos:...",
  "suite": "mortalos-confidential-state-suite/1"
}
```

The wrap record contains the exact label digest, recipient/key identifiers, suite,
epoch, and exactly 384 wrapped bytes for the 3072-bit modulus. Wrap records are
sorted by custodian ID, have no duplicate recipient or public-key digest, cover
every current custodian exactly once, and contain no removed custodian.

`unwrapKey("raw", ...)` uses the same label bytes and the locally bound
non-extractable private key, and creates a non-extractable AES-GCM key. OAEP
failure, wrong recipient, wrong label, substituted public key, stale epoch,
duplicate wrap, missing current wrap, removed-member wrap, or unexpected key length
returns one stable wrap error and releases no candidate epoch key.

## 9. Encrypt, recover, and activate

Encryption is layered over S3:

1. Validate the accepted lineage, membership descriptor, resource limits, and
   confidential transition input.
2. Reserve all required invocation counters durably.
3. Encrypt fixed bounded plaintext chunks locally with exact AAD.
4. Construct and verify the ciphertext-only package and every current-member wrap.
5. Store and replicate only ciphertext packages through S3 adapters.
6. Recover ciphertext using S3 inventory/fetch/digest rules.
7. An authorized endpoint unwraps the epoch key and authenticates every chunk.
8. Reconstruct exact plaintext privately and verify its encrypted internal
   commitment.
9. Atomically activate the completely verified epoch/package.

Relay presence, store inventory, ciphertext digest success, OAEP unwrap success, or
GCM decrypt success alone never accepts a lineage transition. The existing protocol
validator accepts only the exact quorum-signed canonical package and receipt.

Missing ciphertext remains `state_unavailable`. Missing local decryption authority
is distinct `key_unavailable`. Authentication or semantic mismatch is
`confidential_state_rejected`. Adapter interruption is
`confidential_state_interrupted`. Error details must not reveal whether a guessed
plaintext, key, tag, label, or individual chunk was close to valid.

## 10. Membership rotation and crash semantics

An accepted membership change from epoch `N` to `N+1` requires:

1. the current quorum-authorized membership successor;
2. exact new-custodian acceptance including encryption-key binding;
3. a fresh epoch key;
4. wraps for every and only the new membership;
5. complete re-encryption of the active plaintext under epoch `N+1`; and
6. atomic activation of the new membership, confidential package, wraps, counter
   state, and active-epoch record.

Every write boundary must recover to one of two complete states:

- old membership plus complete readable epoch `N`; or
- new membership plus complete readable epoch `N+1`.

A mixed membership/key/package state is never active. Until the final atomic commit,
epoch `N` remains the only active state and its ciphertext, wraps, and local key
material are retained. After commit, best-effort deletion may remove local old keys
and staged bytes, but no erasure claim follows.

A custodian removed at `N` receives no `N+1` wrap. Tests give it the complete public
`N+1` capture, every old key and wrap, and its removed private key; decryption must
still fail. Authorized survivors must decrypt exact `N+1` bytes.

If one current encryption key is lost, any surviving authorized custodian that can
decrypt the old epoch may participate in a quorum-approved membership repair and
fresh epoch rotation. If no authorized endpoint can recover an epoch key, state is
`key_unavailable`; it is not empty state, invalid lineage, or death.

## 11. Metadata leakage and capture gate

The public capture leaks the values listed in section 3, including equality and
size patterns within the limits implied by ciphertext structure. S4 does not add
padding in version 1. Applications with sensitive length distributions require a
future versioned padding ADR.

The capture test records every byte offered to the relay and remote-store adapters,
then rejects if it contains:

- the reference plaintext or any designated plaintext marker;
- the raw 32-byte epoch key;
- a private signing or RSA key encoding;
- an unwrapped WebCrypto key export;
- a public plaintext digest designated as confidential; or
- an unexpected unencrypted payload field.

Passing a marker scan is not itself proof of encryption. The test also independently
parses every record as a bounded ciphertext/wrap format and proves exact authorized
decryption from the captured bytes plus only the recipient private key.

## 12. Versioning and migration

All formats and the suite ID are exact. Unknown versions or algorithms fail closed.
A package cannot mix suites, IV constructions, tag lengths, wrap algorithms, or
epoch numbers.

Algorithm migration is a membership-authorized confidential-state transition:

1. approve a new ADR and new suite identifier;
2. retain the old complete readable epoch;
3. decrypt under the old supported suite at an authorized endpoint;
4. create a fresh key and complete package under the new suite;
5. cross-runtime verify both sides; and
6. atomically activate the new suite or retain the old epoch.

Silent parameter upgrades are forbidden. RSA key-size change, hash change, tag
change, padding, multi-resource nonce allocation, hardware-backed keys, or a future
post-quantum/hybrid wrap each requires a new suite.

## 13. Required implementation evidence

S4 implementation remains HOLD until all of the following pass on one frozen source:

- NIST AES-GCM known-answer and negative vectors;
- published RSA-OAEP SHA-256 decrypt/label vectors and malformed-ciphertext
  negatives;
- byte-identical Node WebCrypto and actual Chromium vectors;
- exact JCS AAD and wrap-label fixtures;
- at least 1,000,000 IV allocations with zero duplicates, plus concurrent,
  rollback, stale, and overflow rejection;
- relay and store capture with zero plaintext, raw epoch key, private key, or public
  confidential digest;
- any-two S3 ciphertext recovery followed by exact authorized decryption;
- removed-at-`N` future-epoch denial and authorized-survivor success;
- replay, substitution, truncation, reorder, wrong-resource, wrong-membership,
  wrong-epoch, wrong-label, duplicate-wrap, and authentication-tag rejection with
  no partial plaintext;
- fault injection at every counter, chunk, wrap, package, rotation, and activation
  write boundary, yielding only complete old or complete new epoch;
- unchanged v0/v1 lineage, mortality, S1, S2, and S3 behavior;
- exact receipt `evidence/stages/s4-confidentiality.json`;
- zero high-or-higher and zero total dependency advisories; and
- immutable independent review, expected-head merge, exact-main Verify, Deploy,
  and public readback.

## 14. Rejected alternatives

- **Plaintext at trusted relay:** contradicts the S4 operator-capture threat model.
- **AES-GCM with random 96-bit IVs:** probabilistic collision management is
  unnecessary when a durable deterministic invocation field is available.
- **One nonce derived only from chunk index:** re-encrypting changed content under
  the same epoch could reuse a nonce.
- **RSA-PKCS1-v1_5:** retained by RFC 8017 for compatibility, not selected for new
  key establishment.
- **Reuse Ed25519 signing keys for encryption:** conflates authority and
  confidentiality and is not a valid WebCrypto key conversion.
- **Home-grown ECDH/HPKE:** a custom KEM/KDF/AEAD composition is outside this ADR.
- **Password-derived or user-entered content keys:** creates weak-key and recovery
  ambiguity outside the participant custody model.
- **Convergent/deterministic plaintext encryption:** leaks equality and enables
  confirmation attacks.
- **Decryption as validity:** gives secret holders a second authority path and is
  forbidden.
